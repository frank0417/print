# PrintKit 运行一段时间后卡顿：原因分析

仓库现场（仓储 / ERP 票据）常见现象：**刚打开浏览器打印还顺，连打几小时后整机变慢、预览卡、点打印要等很久**。这不是某一张单特别复杂，而是本机代理是**长驻进程**，几处资源从不回收，用得越久越沉。

## 为什么会“越用越卡”

扩展用 `chrome.runtime.connectNative` 拉起 `com.printkit.host`。只要 Chrome 还连着这个端口，**Node 代理不会退出**。代理里又会再拉一个 **headless Chrome（CDP 转 PDF）**，并且 `detached + unref`，连代理重启后这个 Chrome 都还在。

所以真正在“过夜”的是：

1. Native Host（Node）
2. Headless Chrome（`%TEMP%\printkit-chrome-cdp`）
3. 每次打印留下的临时目录、日志、预览任务 HTML

下面按对卡顿的贡献排序。

---

## 1. Headless Chrome 永不回收（最主要）

`native-host/lib/chrome-cdp.js` 原先：

- 第一次预热 / 转 PDF 时 `spawn(chrome, { detached: true })` + `child.unref()`
- **没有保存 PID，没有空闲退出，没有按任务次数重启**
- `user-data-dir` 固定为 `%TEMP%\printkit-chrome-cdp`

后果（连打几个小时后很典型）：

| 现象 | 原因 |
| --- | --- |
| 内存持续涨 | headless Chrome 渲染进程 / GPU 缓存不释放 |
| 磁盘越来越大 | `Default/GPUCache`、`Code Cache`、`Crashpad` 只写不删 |
| 打印越来越慢 | 同一浏览器实例里 target / 缓存变脏，CDP `printToPDF` 变慢 |
| 任务管理器里多一个长期 Chrome | 代理挂了它还在，下次打印继续往这个进程里堆 |

IPP 激光机还有另一条 **kiosk Chrome**（`printkit-chrome-kiosk`）：每次打印拉一个可见 Chrome，打完 `taskkill`。kill 失败时会留下孤儿进程，Win7 上尤其容易把机器打满。

**处理：** 按「满 40 单或进程活超过 20 分钟」回收 CDP Chrome；10 分钟空闲则关掉；重启时清 kiosk / 普通 headless 的缓存目录。

---

## 2. 临时打印目录从不删除

每次 `print`：

```js
const jobDir = fs.mkdtempSync(path.join(os.tmpdir(), 'printkit-'));
```

里面有 `job.html`、`job.pdf`、kiosk 副本。原先 **打印成功也不删**，`jobDir` 还回传给扩展。

仓储一班几百张单 → `%TEMP%` 里几百个 `printkit-xxxxxx`。磁盘一满，Windows（尤其 Win7）会表现为：

- 资源管理器 / 杀毒扫描 TEMP 卡死
- 新建临时文件变慢（下一次打印更慢）
- 整机“过一会儿就顿”

**处理：** 打印结束后 15 秒删除本次目录；代理启动时清掉超过 2 小时的旧 `printkit-*` 任务目录。

---

## 3. Native 消息读循环泄漏监听器

原先每读一条 Native Message 就：

```js
process.stdin.on('end', () => resolve(null));
process.stdin.on('error', reject);
```

成功读完 **不会 `off`**。代理是长驻的，打 3000 单就挂 3000 个 `end`/`error` 监听。Node 会打 `MaxListenersExceededWarning`，事件分发本身也会越来越慢。

**处理：** 整个进程只挂一对 stdin 监听，用缓冲区拆包。

---

## 4. 日志只追加、不轮转

`printkit-host.log`（以及各模块直接 `appendFileSync`）没有大小上限。每单都会同步写盘。文件到几十 MB 后：

- 每次打印多一次大文件同步 IO
- 部分杀毒会反复扫这个不断变大的日志

**处理：** 超过约 2MB 轮转为 `printkit-host.log.old`。

---

## 5. 预览任务把整页 HTML 留在扩展里

预览路径会把 `pages[].html`（整页 outerHTML + 样式）放进：

- Service Worker 内存 `jobs` Map
- `chrome.storage.session` / `local`

只有点「关闭」或「打印」才发 `CLOSE_PREVIEW`。用户点窗口 **X** 关掉时，任务会留到 30 分钟过期。Native 长连接还会让 MV3 Service Worker **不容易休眠**，这些大字符串就一直占着 Chrome 内存。

业务页表格一复杂，几十次预览就能把扩展进程打肿，表现为点图标、弹预览都卡。

**处理：** 监听 `chrome.windows.onRemoved`，窗口关掉立刻丢掉对应 job。

---

## 6. 其它会放大卡顿、但不是“随时间泄漏”的点

这些是**每单都付的税**。机器已经被上面 1–5 拖慢之后，会感觉更明显：

| 路径 | 说明 |
| --- | --- |
| 每次打印多次拉 `powershell.exe` + WMI | 队列恢复、打印机元数据、等假脱机、断言任务；Win7 WMI 经常 1–2 秒/次 |
| `Page.printToPDF` + `ReturnAsBase64` | 整份 PDF 进 Node 堆，单次峰值高，一般能被 GC 掉 |
| 针式 GDI | 每次新 PowerShell + `LoadLibrary pdfium`，打完会 `DestroyLibrary`，不累积，但机器忙时更慢 |
| 业务页 `inject.js` | 把 page1…N 的 outerHTML 经 `postMessage` 丢给扩展；页越大越卡，这是单次成本 |

打印机队列里若有 IPP/WSD **Error 作业堵着**，后面的任务会“已发送但不出纸”，操作员反复点打印，进一步堆 Chrome / TEMP。现有 `recoverWinPrinterQueue` 就是为这个写的，和内存泄漏是另一类问题。

---

## 现场怎么确认

在已经卡顿的电脑上：

1. 任务管理器：是否有长期 **chrome.exe / msedge.exe**，命令行带 `printkit-chrome-cdp` 或 `printkit-chrome-kiosk`
2. 看 `%TEMP%`：`printkit-*` 目录是否成百上千；`printkit-host.log` 是否很大
3. 看 `printkit-host.log` 是否刷屏 `MaxListenersExceededWarning` 或 CDP 越来越慢
4. Chrome `chrome://extensions` → PrintKit → 检查视图，内存是否异常高

清 TEMP、结束 headless Chrome、重载扩展后若立刻好转，就可以认定是本分析中的泄漏，而不是打印机驱动本身。

## 本次代码改动（对应上面 1–5）

- `native-host/lib/hygiene.js`：删目录、轮转日志、按 user-data-dir 杀我们自己的 Chrome
- `native-host/lib/chrome-cdp.js`：记录 PID / 任务数 / 启动时间，超时或满额回收，空闲退出
- `native-host/host.js`：stdin 单监听；打印后删 job 目录；启动时清陈旧 TEMP
- `extension/background/service-worker.js`：预览窗关掉即释放 job
